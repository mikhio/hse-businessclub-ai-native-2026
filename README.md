# Свои люди — модуль стартапов и вакансий

Тестовое задание AI-native разработчика для Бизнес-клуба НИУ ВШЭ. Рабочий прототип: участник публикует стартап или вакансию, другой участник откликается, автор принимает решение, а кандидат видит его в кабинете.

**Все аккаунты, проекты и отклики в демонстрации вымышленные.** Исходный код подготовлен для открытой сдачи тестового задания. Заявка клубу автоматически не отправляется.

## Запуск

Нужны Docker Engine и Docker Compose v2+.

```bash
docker compose up --build -d
```

Открыть **http://localhost:8173**. API-документация: http://localhost:8173/docs. Проверка готовности: http://localhost:8173/health.

Swagger на `/docs` загружает свои JavaScript/CSS из jsDelivr, поэтому для этой страницы нужен интернет. Разрешение CDN и nonce для инициализации ограничены маршрутом `/docs`; основной интерфейс не использует CDN и сохраняет строгую CSP.

Переменные имеют демонстрационные значения по умолчанию, поэтому для первого запуска копировать `.env` не требуется. Для своих настроек скопировать `.env.example` в `.env`. Порт задаётся через `APP_PORT`. База не публикует порт на хост, приложение слушает только loopback-интерфейс. Данные сохраняются в именованном Docker volume `club_data`.

Остановить без потери данных:

```bash
docker compose down
```

Следующий `docker compose up -d` поднимет ту же базу. `docker compose down -v` удаляет демонстрационные данные; эта команда не нужна для обычной остановки.

## Как проверить основной сценарий

1. В обычном окне войти как Анна. Нажать «Создать публикацию», заполнить тип, название, описание, роль и формат работы, опубликовать.
2. В приватном окне или другом браузере войти как Максим. Найти публикацию в ленте, открыть и отправить сообщение автору.
3. У Анны открыть «Входящие отклики» и принять либо отклонить новый отклик. Подтвердить решение.
4. У Максима открыть или обновить «Мои отклики». Виден сохранённый результат.
5. Войти как Мария: в её кабинетах чужого отклика нет. Через API нельзя изменить чужую публикацию или принять решение за автора — сервер вернёт `403`.
6. Перезапустить приложение: публикация, отклик и решение остаются в PostgreSQL.

В начальных данных уже есть отклик Максима на StudyPal, поэтому входящий сценарий можно посмотреть без создания новой публикации.

## Модель и решения

**Стек:** Python 3.12 в контейнере, FastAPI, SQLAlchemy 2.0, PostgreSQL 16, HTML/CSS/JavaScript без сборки фронтенда. Зависимости закреплены в `requirements.txt`; диапазоны для обновления — в `requirements.in`.

Выбрал один backend и статический клиент на том же origin: для прототипа это снижает число компонентов и убирает необходимость в CORS и отдельном frontend-сервере. Интерфейс получает данные через JSON API. Ключевые правила находятся на сервере; скрытая кнопка не считается проверкой доступа.

| Сущность | Основные поля |
|---|---|
| `users` | email, имя, специализация, описание, навыки, scrypt-хэш пароля |
| `login_sessions` | SHA-256-хэш случайного токена, пользователь, CSRF-токен, срок действия |
| `publications` | автор, тип, название, описание, кого ищет, формат, статус, дата, ключ создания |
| `applications` | публикация, кандидат, сообщение, статус, дата отправки и решения |

Публикация переходит между `open` и `closed`. Закрытие убирает её из обычной ленты и запрещает новые отклики, но сохраняет предыдущие и позволяет принять решение по ним. Автор может снова открыть набор. Изменение содержания и удаление публикаций в эту версию не входят.

Отклик имеет состояния `pending → accepted` или `pending → rejected`. Решение окончательное. Повтор такого же решения безопасен, противоположное возвращает `409`. На одну публикацию у участника один отклик, на свою публикацию откликнуться нельзя.

При повторной отправке отклика возвращается уже существующий результат, даже если набор после этого закрыли. Уникальное ограничение в PostgreSQL и блокировка строки публикации защищают от конкурентных дублей. Закрытие набора использует ту же блокировку. Решение автора блокирует строку отклика, поэтому два одновременных противоположных решения не перезаписывают друг друга.

Создание публикации поддерживает `Idempotency-Key` длиной до 80 символов. Клиент генерирует один ключ на открытую форму и повторно использует его после сетевой ошибки. Одинаковый ключ и содержание возвращают ту же публикацию; смена содержания с уже использованным ключом возвращает `409`. Без ключа каждый запрос считается отдельным намерением создать публикацию.

## API

Все `/api/*`, кроме входа, требуют cookie-сессию. Изменения требуют `X-CSRF-Token`, полученный из входа или `GET /api/me`.

| Метод и адрес | Назначение |
|---|---|
| `POST /api/auth/login` | Вход по email и паролю |
| `POST /api/auth/logout` | Отозвать текущую сессию |
| `GET /api/me` / `PATCH /api/me` | Профиль и его редактирование |
| `GET /api/publications` | Лента: `kind`, `q`, `status`, `mine`, `limit`, `offset` |
| `POST /api/publications` | Создать публикацию; необязательный `Idempotency-Key` |
| `GET /api/publications/{id}` | Подробности и только свой отклик |
| `PATCH /api/publications/{id}` | Автор меняет статус набора |
| `POST /api/publications/{id}/applications` | Отправить отклик |
| `GET /api/applications?direction=sent` | Отправленные отклики |
| `GET /api/applications?direction=received` | Отклики на свои публикации |
| `PATCH /api/applications/{id}` | Автор принимает либо отклоняет отклик |

## Безопасность и границы

Пароли хранятся в scrypt с индивидуальной солью. Cookie сессии имеет `HttpOnly`, `SameSite=Strict` и ограничение в 12 часов. В базе хранится хэш токена сессии, а не cookie. Выход удаляет сессию на сервере. Для HTTPS-развёртывания нужно включить `COOKIE_SECURE=true`.

Запросы изменения данных проверяют CSRF и права пользователя. SQL-запросы параметризованы. Пользовательский текст экранируется перед выводом, inline JavaScript и сторонние ресурсы запрещены CSP. Данные API не кешируются. Имена/навыки видны участникам, email и текст чужих откликов в ленту не попадают.

Это локальное демо с известными паролями, а не готовая публичная система. Для реального клуба потребуются Telegram-аутентификация с проверкой `initData`, выдача аккаунтов, ограничение частоты входа, политика хранения данных и полноценные миграции. Сейчас схема создаётся `create_all` при первом запуске; изменение уже существующей схемы нужно выполнять отдельной миграцией. Сессионные строки с истёкшим сроком не используются, но автоматическая уборка ещё не реализована. Уведомлений, чата между участниками и Telegram SDK нет — в ТЗ нужен веб-прототип модуля. Деплой является бонусом и в этой версии не выполнялся.

## Проверки

С настоящим PostgreSQL, в автоматически создаваемых отдельных схемах, без удаления данных демонстрации:

```bash
docker compose --profile test run --rm tests
```

16 тестов проверяют основной сценарий, права третьего пользователя, CSRF, выход, хэширование сессии, сохранение профиля в новом входе, фильтры и пагинацию, ошибки, собственную публикацию, закрытый набор, повторные действия, конкурирующие запросы и изоляцию CSP документации. Результаты проверок записаны в `VERIFICATION.md`.

Дополнительная браузерная проверка (Node.js + Playwright):

```bash
npm install --no-save --package-lock=false playwright
npx playwright install chromium
node tests/browser.mjs
```

Скрипт запускает свой браузер, проверяет отрисовку операций Swagger без нарушений CSP, проходит сценарий двумя аккаунтами, проверяет отсутствие горизонтального переполнения на ширинах 320, 390, 768 и 1440 px и сохраняет скриншоты в `artifacts/`. Использует вымышленные demo-аккаунты; создаёт дополнительную вымышленную публикацию. Адрес можно задать через `APP_URL`, путь уже установленного Chromium — через `CHROMIUM_PATH`.

## Использование ИИ

Я поручил Codex превратить общее продуктовое задание в работающий модуль: выбрать модель данных и API, реализовать backend и интерфейс, подготовить Docker Compose, тесты и документацию. Реализацию и проверку выполняли агенты; я задавал цель и поручил отдельное независимое ревью результата.

Конкретный пример проверки предложенного ИИ-решения — страница Swagger. В исходном варианте общая CSP блокировала JavaScript и CSS документации, хотя `/docs` отвечал HTTP 200. Независимый агент воспроизвёл проблему в Chromium. Исправление ограничили маршрутом `/docs`: разрешили необходимые ресурсы Swagger и добавили одноразовый nonce для инициализатора, сохранив строгую политику основных страниц. Повторная проверка показала 11 операций Swagger без нарушений CSP; отдельный регрессионный тест проверил уникальность nonce и изоляцию политики. Основной браузерный сценарий и 16 тестов также прошли.
